## 공개 배포용 사본

- 사용자 승인에 따라 `publish/0925_공개용_통일조판본.hwpx`는 계정 정보 메모를 제거한 별도 배포 사본으로 관리한다. 원본·단일 누적 작업본은 변경하지 않는다.
- 공개용 사본은 새로운 누적 편집 기준본이 아니다. 후속 편집은 기존 단일 누적본에 계속 반영한다.
- 공개 저장소에는 `publish/`의 보안 검수 완료 산출물만 올린다. 내부 HWPX, 원본 PDF, `draft/`, `render/`, 임시 `.review*`는 업로드하지 않는다.
- 계정 정보는 XML 본문·메모, 추출 텍스트, 미리보기, 실제 출력 PDF까지 확인한다. 민감 값 자체를 로그나 검증 기록에 남기지 않는다.
- 파일에서 계정 정보를 제거해도 이미 노출된 비밀번호의 변경 필요성은 사라지지 않는다.

## 누적 산출물 원칙

- 쪽별 요청은 해당 쪽만, 여러 쪽의 공통 조판 요청은 지정된 전체 범위를 작업한다. 여러 쪽을 수정할 때도 각 쪽의 실제 렌더를 확인한다.
- 수정 범위 밖의 지면은 보존한다. 지정된 범위에서 표 구조를 바꿀 때는 본문·보기·그림 참조 보존을 별도 검사한다.
- `hwp/` 최상위에는 쪽별 완료본을 만들지 않고 단일 누적 작업본만 유지한다.
- 쪽별 검수용 임시본과 교체 전 백업은 `draft/`에 쪽수와 상태가 드러나는 이름으로 보관한다.
- 검수 전에는 `draft/..._{쪽수}쪽_검수중.hwpx`를 사용한다. 실제 한컴 시각 검토까지 통과한 뒤 단일 누적 작업본을 교체한다.
- 단일 누적 작업본을 교체하기 전 기존 파일은 `draft/`에 백업한다.
- 삽화를 삽입하거나 교체한 같은 작업에서 `삽화_사용목록.md`를 반드시 갱신한다.
- Git 커밋·푸시는 사용자가 명시적으로 요청한 경우에만 수행한다.

## 3쪽에서 확정된 배치 기준

3쪽 완료본은 이후 쪽의 품질 기준이다.

- `먼저 질문해요`의 학생 삽화는 왼쪽 질문 셀에 둔다.
- `이렇게 확인해요`의 사실 확인·개인정보 보호·출처 표시·인공지능 활용 아이콘은 오른쪽 설명 셀에 둔다.

## 삽화 선택과 배치 규칙

1. 작업할 쪽의 `../pic/{쪽수}쪽_*.png`를 모두 확인한다.
2. `../pic/삽화_리스트.md`에서 각 파일의 의미와 권장 위치를 읽는다.
3. HWPX의 해당 쪽을 한컴에서 열어 제목·본문·표·셀·제작 지시문을 실제 화면으로 확인한다.
4. 삽입 전에 다음 대응표를 작업 메모로 확정한다.

| 삽화 파일 | 대상 쪽·영역 | 정확한 셀·문단 | 유지/삭제할 제작 지시문 | 선택 이유 |
|---|---|---|---|---|

5. 인물·장면은 질문, 사례, 활동을 보여 주는 셀에 둔다. 설명용 아이콘은 그 의미를 설명하는 셀이나 제목 옆에 둔다.
6. `삽화 설명:`, `아이콘 설명:`, `[아이콘 설명: ...]` 같은 문구는 제작 지시문이다. 대응 삽화가 실제로 삽입된 경우에만 해당 지시문을 삭제한다.
7. 학생이 읽어야 하는 본문·질문·보기·표 제목은 삭제하거나 이미지로 대체하지 않는다.
8. 순수 삽화를 기본으로 사용한다. 한글 문구가 장면 의미에 필수이고 별도 조판이 불가능할 때만 글자 포함본을 선택한다.
9. 글자 포함본을 사용할 때는 원문의 한글·숫자·문장 부호가 정확한지 눈으로 다시 확인한다.
10. 같은 공통 아이콘을 양쪽에서 반복 사용하는 경우에는 동일 이미지 자원을 재사용할 수 있다. 단, 각 위치에서 실제 표시 여부를 따로 확인한다.
11. 삽화가 활동의 정답을 미리 알려 주는 위치나 강조를 만들지 않는다.

## HWPX 편집 기술 규칙

- 비대상 ZIP 엔트리, 기존 본문, 표, 스타일, 그림을 보존한다.
- 그림 파일을 `BinData/`에 넣은 것만으로 삽입 완료라고 판단하지 않는다.
- `Contents/content.hpf`의 이미지 항목, 본문의 `binaryItemIDRef`, 실제 `BinData` 파일을 함께 맞춘다.
- 새 `hp:pic`의 `id`와 `instid`는 섹션 안에서 중복되지 않게 한다.
- 이미지 비율을 보존하고 대상 셀의 폭·높이를 넘지 않게 한다.
- macOS 한컴에서 새 그림이 무시되지 않도록 `hp:pic` 안의 `hc:img`는 한컴 저장본과 같은 순서로 둔다. 현재 기준은 `hp:renderingInfo` 다음, `hp:imgRect` 앞이다.
- 가능하면 실제로 표시되는 기존 `hp:pic` 구조를 복제하고 이미지 참조·크기만 바꾼다.
- 텍스트를 교체·삭제·추가한 뒤에는 모든 `<hp:linesegarray>`를 제거한다.
- 정적 XML 참조 수와 실제 한컴 화면 표시는 별개다. 그림 참조가 존재해도 화면에 안 보이면 실패다.
- 표 셀 높이는 자동 확장 동작을 우선 보존한다. 임의로 고정 높이를 크게 늘려 다음 쪽을 밀어내지 않는다.

## 쪽별 작업 절차

### 1. 사전 확인

- 원본과 시작 기준본의 SHA-256을 기록한다.
- 시작 기준본이 직전 쪽까지 검수된 파일인지 확인한다.
- 작업할 쪽의 모든 삽화와 글자 포함 변형을 비교한다.
- 해당 쪽 전체와 필요한 확대 영역을 한컴에서 확인한다.
- 제작 지시문과 학생용 문구를 구분한다.

### 2. 후보 파일 작성

- 단일 누적 작업본을 복사해 `draft/..._{쪽수}쪽_검수중.hwpx`를 만든다.
- 이번 쪽의 삽화만 삽입하고 필요한 제작 지시문만 삭제한다.
- 이전 완료 쪽이나 이후 미작업 쪽의 본문·그림을 수정하지 않는다.
- 삽입 이미지의 파일 해시와 HWPX 내부 이미지의 해시를 대조한다.
- 실제 삽입한 파일, 정확한 배치, `BinData` ID와 검수 상태를 `삽화_사용목록.md`에 기록한다.

### 3. 정적 검사

스킬 경로는 `/Users/taeho/.codex/skills/hwpx/scripts`이다.

```text
python3 /Users/taeho/.codex/skills/hwpx/scripts/fix_namespaces.py 후보.hwpx
python3 /Users/taeho/.codex/skills/hwpx/scripts/fill_hwpx.py check 후보.hwpx --strict
python3 /Users/taeho/.codex/skills/hwpx/scripts/validate.py 후보.hwpx --layout
unzip -t 후보.hwpx
```

필수 확인 항목:

- `fill_hwpx.py check --strict`의 `ok`가 `true`이다.
- `linesegarray`가 0이다.
- ZIP 압축 오류가 없다.
- 추가한 모든 그림 참조가 실제 `BinData`와 연결된다.
- 제작 지시문을 삭제한 경우 목표 문구만 사라지고 학생용 문구는 남아 있다.

### 4. 실제 한컴 시각 검토

- 후보 파일을 한컴에서 새로 연다. 이미 열려 있던 이전 파일 화면을 재사용하지 않는다.
- 작업한 쪽의 위·아래 전체를 스크롤해 확인한다.
- 확대 화면에서 다음을 모두 확인한다.
  - 모든 삽화가 실제로 보인다.
  - 삽화가 의미에 맞는 셀·문단에 있다.
  - 인물과 설명 아이콘이 서로 바뀌지 않았다.
  - 제작 지시문이 남아 있지 않다.
  - 본문·표·보기·번호가 보존됐다.
  - 삽화 비율이 깨지지 않았다.
  - 셀 밖 잘림, 글자 겹침, 행 밀림, 빈 페이지 추가가 없다.
  - 이전에 완료한 쪽의 배치가 유지됐다.

정적 검사만 통과하고 실제 한컴에서 보이지 않는 그림이 하나라도 있으면 완료본이 아니다.

### 5. 완료본 승격

- 시각 검토를 통과한 후보만 단일 누적 작업본으로 교체한다.
- 교체 전 누적 작업본은 `draft/`로 옮긴다.
- 원본 SHA-256이 작업 전과 같은지 다시 확인한다.
- 단일 누적 파일명으로 다시 열어 같은 화면이 표시되는지 확인한다.

## 전체 완료 후 렌더 및 Visual QA

- 9쪽까지 누적 작업을 마친 뒤 전체 9쪽을 PDF와 페이지별 PNG로 렌더링한다.
- Windows와 macOS 모두 스킬의 자동 렌더러를 사용한다. macOS에서는 설치된 한컴 앱을 접근성 UI 자동화로 열어 PDF를 내보낸 뒤 페이지별 PNG로 변환한다.

```text
python3 /Users/taeho/.codex/skills/hwpx/scripts/render_hwpx.py 누적본.hwpx --output-dir 새_빈_검토폴더 --expected-pages 9
```

- macOS 자동화 전에 렌더할 HWPX가 한컴에서 이미 열려 있지 않은지 확인한다. 자동화는 자신이 연 문서 창만 닫고 다른 한컴 문서 창은 건드리지 않는다.
- `document.pdf`는 한컴 조판 결과를 전달하는 중간 산출물이다. `page-*.png` 생성과 `--expected-pages` 검사는 렌더 성공 여부를 확인하지만, 그 자체가 Visual QA 완료를 뜻하지 않는다.
- 생성된 9장의 PNG를 전부 직접 열어 제목 계층, 삽화 누락·오배치, 잘림·겹침, 표 밀림, 빈 페이지를 시각 검토한다.
- `render.json`의 `render_ok: true`와 `page_count_check.ok: true`를 확인하고, 전 페이지 육안 검토까지 끝나야 Visual QA 완료다.
- 렌더 산출물은 `hwp/render/` 아래의 새 검토 폴더에 저장하고, 작업 HWPX와 구분한다.

### 지면 끝단과 여백의 최종 검수

- 외곽선 높이가 같다는 이유만으로 좌우 조판이 맞았다고 판단하지 않는다. 마지막 활동표·답안선·삽화·본문이 실제로 끝나는 높이와 프레임 안쪽 하단 여백을 함께 확인한다.
- 쪽별 내용량에 맞게 활동 사이 간격, 표 행 높이, 필기 공간, 삽화 크기를 조정한다. 큰 빈칸 하나로 내용을 아래로 밀거나 글자 크기를 줄여 끝단만 맞추지 않는다.
- 제목·본문·날개단의 글꼴과 크기는 유지한다. 답안 문단의 간격 등 공간 배분에 필요한 예외는 디자인 시스템에 기록한다.
- 삽화는 종횡비를 유지한다. 같은 활동의 두 장면은 위쪽 기준도 비교하며, 표 안의 설명은 같은 높이에서 읽히게 한다.
- 중첩 표는 오른쪽·아래쪽 선이 부모 영역에 걸리지 않도록 안전 여백을 확보하고 실제 렌더에서 네 변을 확인한다.
- 한컴의 자동 확장 높이는 XML 선언 높이와 다를 수 있다. 숫자만 맞추지 말고 렌더를 반복해 보정한다. 1600×1028 교정 PNG에서는 본문 끝단의 좌우 차이를 약 3px 이내로 점검하되, 광학적 균형과 필기 공간도 육안으로 판단한다.
- 검수된 후보를 기존 누적 파일명으로 교체한 뒤 다시 열고 출력이 같은지 확인한다.

## 표 배치 경고 해석

- 원본과 초기 3쪽 완료본의 `validate.py --layout` 경고 기준값은 47건이다. 새 표 구조에서는 표 번호가 달라지므로 숫자만 비교하지 않는다. 최신 경고 수와 검토 결과는 `최종조판_검토기록.md`를 확인한다.
- 이 경고는 자동 높이 셀을 검사기가 `estimated_cell_overflow` 또는 `invalid_cell_geometry`로 추정한 휴리스틱 결과다.
- 47건을 실제 표 결함 47개라고 보고하지 않는다.
- 경고 수가 기준보다 늘거나 새 위치에 경고가 생기면 원인을 확인한다.
- 경고 수가 같더라도 실제 한컴 화면에 잘림·겹침이 있으면 실패다.

## 페이지별 보류 사항

- 5쪽 의사 사진 활동은 복수 답안 가능성 문제가 있다. 사용자의 별도 요청 없이 문항을 고치거나 삽화로 정답을 암시하지 않는다.
- 8쪽은 모든 인공지능 요청이 데이터 센터를 거친다고 일반화될 수 있다. 사용자의 별도 요청 없이 본문을 수정하지 않는다.
- 9쪽 HWPX 토큰 비용은 2026-09-26 사용자 제공 이미지로 확정했다. 글·그림 작성 카드는 각각 위에서부터 2·1·3·1토큰, 나의 생각 카드는 두 항목 모두 0토큰이다. 최종안 PDF 원본의 미확정 상태와 혼동하지 않는다.
- 글자 포함 변형은 편집 참고용일 수 있다. 순수 삽화와 중복 삽입하지 않는다.

## 완료 보고 형식

완료 보고에는 다음 내용을 간결하게 포함한다.

- 완료한 쪽과 삽입한 순수 삽화 수
- 삭제한 제작 지시문과 보존한 학생용 문구
- 실제 한컴 화면에서 확인한 배치 결과
- 수행한 엄격 검사·ZIP 검사·원본 해시 확인
- 9쪽 전체 완료 시 PDF·PNG 렌더 결과와 전 페이지 Visual QA 결과
- 남아 있는 보류 사항
- 절대 경로의 클릭 가능한 최종 HWPX 링크

실제 파일 저장, 정적 검사, 해당 쪽 한컴 시각 검토가 모두 끝나기 전에는 해당 쪽을 완료했다고 보고하지 않는다. 9쪽 전체 작업은 전체 렌더와 9쪽 Visual QA까지 끝나기 전에는 최종 완료라고 보고하지 않는다.
